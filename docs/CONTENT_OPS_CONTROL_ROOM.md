**Audience:** MK (founder), non-technical.
**Purpose:** where content-ops work actually lives at each stage, how to judge whether a piece of work is good, and why research work you can see in the repo is not the same as something live on the public site.

## 2. System of record — who owns what

| Layer | What it is | Where it lives | Is it public? |
|---|---|---|---|
| Queue / inventory | The prioritised list of what needs work, generated from a gap audit | `content/ops/content-inventory.json` / `.csv`, `content/ops/task-queue.json` | No — repo file |
| Research JSON | One agent's proposed facts for one item (operator, region page, itinerary) | `data/research/content-ops/<item-id>.json` | No — a proposal, not applied content |
| Jules session / patch | A single research-only agent run against a task; identified by a numeric session ID, viewable in the Jules web app and (where CLI/API access is set up) pullable via `jules remote list --session` / `jules remote pull --session <SESSION_ID>` | Jules' own session store, not this repo | Not public — an authenticated account holder can view the session at `https://jules.google.com/session/<SESSION_ID>`, but that is private to the account, not a public URL, and does not mean the content is in this repo, the database, the CMS, or the public site |
| Git branch / PR | Reviewed, merged code or content change | GitHub, this repo | Not until merged **and** deployed |
| Database | The actual data the site renders from (operators, activities, regions, etc.) | Neon Postgres, via Drizzle (`src/db/schema.ts`) | Yes, for rows with `status = 'published'` — this is the real source of truth for live pages |
| Admin dashboard | Read-only-ish monitoring + decision-recording UI over the files/DB above | `/admin/content-ops` (`src/app/admin/content-ops/page.tsx`) | Only if deployed and you're signed in as admin |
| Vercel / public site | The actual live pages a visitor sees | Vercel deployment (config: `vercel.json`, `.vercelignore`) | Yes, once deployed — but this document does not confirm there is currently a live deployment; see §5 |

The important distinction: **queue → research JSON → Jules output** are all steps 1–3 of the diagram. None of them touch the database. A file existing in `data/research/content-ops/` means Jules proposed something — it says nothing about whether it's live.

## 3. Where MK can look today

- **`content/ops/status-report.md`** — human-readable snapshot: inventory size, status counts by channel, current launch-visible blockers, top queued tasks. Regenerated by `npm run content-ops:report`. This is the fastest "what's the state of things" read.
- **`content/ops/task-queue.json`** — the raw, priority-ordered queue every agent task comes from. Large (100+ items); read `status-report.md` first.
- **`data/research/content-ops/`** — one JSON file per researched item (operators, region landings, itineraries). Each has a `_meta` block with `recommendedNextStatus`, `identityConfidence`, and `redFlags`. **This is a proposal folder, not published content** — a file here has no effect on the live site until a human reviews it and applies it.
- **`/admin/content-ops`** — when an authorised deployment is available. Shows inventory counts, the commercial-decision queue, and launch-visible blockers by reading the files above (plus `content/ops/commercial-decisions.json`). It does **not** currently read the database for content status, and decision buttons on it write to a JSON file, not the database — see §5 for the durability caveat.
- **Jules sessions** — research-only agent runs, referenced by numeric session ID (e.g. `jules remote pull --session 2730327055973848465`). An authenticated account holder can view a session in the Jules web app at `https://jules.google.com/session/<SESSION_ID>`; sessions can also be listed/pulled via the Jules CLI or API where that access is set up (the CLI is not currently installed on this machine). Either way, viewing or pulling a session is private to the account — a Jules session existing does not mean anything reached this repo, the database, the CMS, or the site; only a pulled, reviewed, applied patch does.

None of the above is a public URL. If you want to check what's actually live, the only correct source is the deployed site itself (or a direct look at `operators.status = 'published'` and equivalent rows in the database) — not a file in this repo.

## 4. Quality gates — what has to happen before anything is public

In order, per the operator/content workflow (`vault/workflows/operator-verification-publishing.md`, `vault/workflows/content-ops-pipeline.md`):

1. **Source evidence** — every non-obvious factual field must cite a source URL (`data/research/content-ops/_ENRICHMENT_SPEC.md`). Seed CSV data alone (`data/wales/Wales database - Operators.csv`) is never sufficient — it's known to contain fabricated phone numbers, emails and ratings.
2. **Identity/region validation** — agent must confirm the business is who it says it is (`identityConfidence`: HIGH/MEDIUM/LOW) and that it actually operates in the region it's being attached to, against the operator's own site.
3. **Image rights/location** — real, licensed, attributed images only; no AI-generated images of real places, businesses or people (`vault/workflows/image-sourcing.md`).
4. **Schema validation** — every inventory/queue file is checked against a Zod schema (`scripts/content-ops/schemas.ts`) before it's used; invalid entries are skipped with a warning rather than silently accepted.
5. **Human editorial review** — a second, adversarial verify pass (higher-capability model) re-checks the first agent's proposal before anyone applies it. `recommendedNextStatus = "published"` is only allowed if identity is HIGH-confidence **and** name, website, phone and at least one activity are all confirmed — otherwise it's routed to `review`.
6. **DB apply** — the actual publish step: a human (or a merged, reviewed change) sets the row's `status` to `published` in Postgres. Public queries filter to published-only (`src/lib/queries/operators.ts`), so nothing in `draft` is visible regardless of what research files say.
7. **Build / typecheck / tests** — `npm run typecheck`, `npm run lint`, `npm test`, `npm run build` all run in CI on every push and PR (`.github/workflows/ci.yml`). A change that breaks any of these doesn't ship.
8. **Link crawl** — after a build, crawl every internal link from the live-rendered site and check status codes, to catch broken links the UI would otherwise mask (`npm run content-ops:links`; documented method in `vault/workflows/content-ops-pipeline.md`).
9. **Explicit publish decision** — for commercial/operator content specifically, a human records a tiering decision (strategic anchor / premium lure / claimed / stub / blocked) before treatment changes. The dashboard is explicit that clicking a decision button "does not publish content" and "does not change production operator tier automatically" (`src/app/admin/content-ops/decisions/route.ts`).

## 5. Current reality and gaps

- **Jules is scoped to research; Claude Code is scoped to development.** Neither is permitted to publish, deploy, send outbound email, or change the production database on its own initiative — every one of those requires explicit human approval.
- **Research output is a proposal, not a DB update.** A file appearing in `data/research/content-ops/` means an agent did research and wrote a JSON file to disk. It has not been reviewed, has not been applied, and has no effect on the live site.
- **`/admin/content-ops` is currently file-backed, and its decision route is not durable.** The dashboard reads JSON files, not the database, for content status. Its decision-recording endpoint (`src/app/admin/content-ops/decisions/route.ts`) writes to `content/ops/commercial-decisions.json` on local disk — the code itself documents that this write is lost on Vercel's read-only/ephemeral filesystem on the next deploy or instance recycle, and logs a warning rather than crashing when that happens. **Update:** the durable replacement schema already exists — `listing_evidence`, `content_review_state`, and `ops_decisions` tables were added to `src/db/schema.ts` and shipped in migrations `drizzle/0002_tidy_toad_men.sql` / `drizzle/0003_simple_blue_marvel.sql` (2026-08-24) — but as of this writing nothing in the application reads or writes them yet (only the schema file and its test, `src/db/__tests__/fact-check-schema.test.ts`, reference them). The dashboard and decision route still use the non-durable file path. Wiring this up is the concrete next step in §8.
- **No agent may publish, deploy, send outbound email, or change the production database without explicit approval.** This applies uniformly across the pipeline, regardless of which agent or tool produced the work.
- **No live deployment is confirmed here.** `vercel.json` and `.vercelignore` show the project is configured for Vercel, but this document does not verify there is currently a live, publicly reachable deployment or CMS — that should be checked against the actual Vercel project, not inferred from repo files.

## 6. Operational review cadence

Two separate schedules are actually running, from two separate places:

- **In this repository, verifiable via git:** a single scheduled GitHub Action, **Content Ops Nightly** (`.github/workflows/content-ops-nightly.yml`), runs once daily at 03:00 UTC. It runs `npm run content-ops:audit` and `npm run content-ops:report` (filesystem-only — inventory/queue/status-report regeneration) and commits the result back to `content/ops/`. It does not run research, does not touch the database, and needs no secrets.
- **In the active Adventure Wales operational system, outside this repository:** a research pulse runs every 30 minutes under the MiniGeek Hermes profile. It picks up the next `research_needed` items from the queue and submits **research-only** Jules tasks (writing proposal JSON, per §2) — it does not publish, apply, or deploy anything. This pulse is operational configuration owned by that profile, not a file in this repo, so nothing in this repo's git history or worktree confirms it on its own; it's described here based on how the operator has configured it, separately from what git can show.

On top of both of those:

- **Each morning:** an exception report — a human-readable summary of what's blocked, what needs a decision, and what changed overnight (today, the closest equivalent already automated in-repo is the nightly audit above).
- **Ongoing:** a human review queue — nothing moves past `qa_needed`/`reviewed` without a person looking at it, via the gates in §4.
- **Bounded Claude Code implementation tasks:** development work (dashboard, schema, scripts — like this document) is scoped to specific, narrow tasks, not open-ended "finish the site" instructions. Claude Code does not run research passes or write proposal JSON — that's Jules' job (§5).

## 7. Quality scorecard (plain-English)

For any single piece of content (an operator page, a region page, an itinerary), six checks, each red/amber/green:

| Check | 🟢 Green | 🟡 Amber | 🔴 Red |
|---|---|---|---|
| **Evidence** | Every fact has a cited source URL, not just the seed spreadsheet | Some fields sourced, some not | No sources beyond the (known-unreliable) seed CSV |
| **Accuracy** | Identity confirmed HIGH confidence against the operator's own site | MEDIUM confidence, or minor discrepancies flagged | LOW confidence, or a red flag raised (wrong region, closed business, placeholder contact info) |
| **Image rights** | Real, licensed, correctly-attributed image of the actual place/business | Image present but provenance/licence not yet confirmed | No usable image, or an AI-generated image of a real place/business (not allowed) |
| **Editorial usefulness** | Reads as genuinely useful, specific, non-generic; a human has reviewed it | Drafted but not yet reviewed by a person | Flagged as generic filler, or blocked pending a fix |
| **Technical validity** | Passes schema validation, typecheck, lint, tests and build | Passes but with warnings, or not yet re-validated after a change | Fails validation, typecheck, or build |
| **Approval state** | A human decision is recorded and the DB row is `published` | Awaiting a decision (`qa_needed` / `reviewed`, no decision yet) | `blocked`, or explicitly rejected |

A page isn't ready for the public site until every row is green. Amber means "in progress, don't judge it yet." Red means "don't trust this content as-is."

## 8. Next two concrete improvements

1. **Durable review/apply dashboard.** The database tables for this already exist (`listing_evidence`, `content_review_state`, `ops_decisions` — see §5) but nothing reads or writes them yet. Wire `/admin/content-ops` and its decision route to these tables instead of local JSON files, so review state and commercial decisions survive a Vercel redeploy instead of being silently lost.
2. **A deployable, authenticated quality view.** Once #1 gives the dashboard something durable to read from, expose the §7 scorecard behind admin auth on an actual deployment, so MK can check content status directly without pulling a local worktree or asking someone to run scripts.
